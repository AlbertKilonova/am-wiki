AlightMotionWiki 设计白皮书

版本 2.0 · 2026-11-13 主题：无后端静态 Wiki 的内容生产体系 站点：AlightMotionWiki（社区维护的 Alight Motion 知识库）

1. 摘要

本次重建把一份仅剩 HTML 骨架的旧社区站点，重建为：

  • 纯静态的 Vue 3 单页应用（无服务端、无数据库、无运行时依赖）
  • 内容以 Markdown 文件为唯一真相源，构建时打包进产物
  • 编辑通过 浏览器内 CMS 完成，提交形式是 GitHub Pull Request
  • 质量门禁与部署交给 GitHub Actions

一句话概括设计目标：让"改内容"变成一次可审阅、可回滚、可自动验证的 PR，同时不养任何服务器。

2. 目标与非目标

2.1 目标

# 目标 验收标准
G1 零服务器运维 仓库之外没有任何需要维护的进程/数据库/密钥服务
G2 内容即文件 每篇文章 = 一个 .md，可被 git 完整追踪
G3 编辑可在线 无需本地环境，浏览器即可新建/修改并发起 PR
G4 变更可审核 任何内容改动都经过 PR，PR 内可见 diff 与构建结果
G5 构建可验证 frontmatter 不合法 / 构建失败时 PR 直接变红
G6 阅读端体验 移动端优先、深浅主题、搜索、动效克制
G7 可访问性 支持 prefers-reduced-motion，语义结构清晰

2.2 非目标

  • 不做用户系统、评论、点赞（需要服务端或第三方）
  • 不做站内图片上传（仓库体积与 clone 成本）
  • 不做多人实时协同编辑
  • 不做服务端搜索索引（文章规模 < 100 时前端内存搜索足够）

3. 信息架构

站点
├─ 首页（分类导航 + 列表）
│   ├─ 01 教程        content/01-tutorial/
│   ├─ 02 下载        content/02-downloads/
│   └─ 03 贡献        content/03-contributions/
├─ 文章页            #/post/<id>
├─ 内容编辑器        #/cms（懒加载，不进主包）
└─ 详情辅助
    ├─ 全站搜索（标题/摘要/正文/标签）
    ├─ 上下篇
    └─ 「GITHUB ↗」直达仓库编辑页

分类与目录的映射集中在一个地方（src/data/categories.js）：

{ id: 'tutorial', label: '教程', desc: '...', dir: '01-tutorial' }
  • id 用于路由与 URL
  • dir 决定 content/ 下的目录，前缀数字决定导航顺序
  • 新增分类 = 加一个数组项 + 建目录，无需改组件

4. 内容模型

4.1 文件格式

每篇文章为一个 Markdown 文件，头部是极简 frontmatter：

---
title: 版本介绍及下载安装
date: 2026-01-03
tags: [Alight Motion, 改版, 入门]
summary: 一句话摘要，显示在列表里
# placeholder: true   # 可选：显示「待补充」
# id: versions        # 可选：默认取文件名
---

正文（完整 Markdown）

4.2 字段约束

字段 必填 类型 校验规则（scripts/validate-content.mjs）
title 是 string 非空
date 是 YYYY-MM-DD 正则 + Date.parse 合法性
summary 否 string 缺失时告警（列表会空）
tags 否 [a, b] 必须是数组语法
placeholder 否 boolean 只接受 true/false
id 否 string 全局唯一，缺省取文件名

4.3 为什么不用 JSON/YAML 数据文件

  • JSON 里写多段 Markdown 需要转义换行，diff 可读性差
  • .md 文件让非技术贡献者能直接读、直接改，GitHub 网页编辑器原生支持预览
  • 目录即分类，文件名即 slug，减少一层映射的心智负担

5. 构建管线

5.1 构建时读取，而非运行时请求

// src/data/posts.js
const files = import.meta.glob('/content/**/*.md', {
  query: '?raw',   // 原样读文本
  import: 'default',
  eager: true,     // 构建时全部内联
})
  • eager + ?raw 让 Vite 在构建阶段把每个 md 的文本内联进 bundle
  • 浏览器打开站点时没有任何内容请求：首屏只有一个 JS + 一个 CSS
  • frontmatter 解析发生在模块初始化（一次性，成本可忽略）
  • 代价：内容变更必须重新构建（这与 PR 工作流天然契合）

5.2 排序与检索

  • 排序：date 降序，同日期按 id
  • 搜索：把 title + summary + body + tags 拼成小写串做 includes；文章量在百级以内时内存搜索的延迟远低于网络请求

5.3 构建脚本（手机环境适配）

/sdcard 是 FUSE 挂载，不支持 pnpm 需要的符号链接。因此 build.sh 采用：

/sdcard/.../am-wiki  ──复制 src/ content/ 配置──►  /root/build/am-wiki
                                                        │ pnpm install + vite build
                                                        ▼
                          dist/  ◄────复制回来────  /root/build/am-wiki/dist

CI 上不存在这个限制，直接 pnpm run build 即可。

6. 无后端 CMS 设计

6.1 方案对比

方案 是否需要后端 用户门槛 安全面 结论
GitHub OAuth App 需 OAuth 代理（secret 不能进前端） 低 中 多人规模再上
细粒度 PAT 直连 API 不需要 中（建一次 token） 中（可限定单仓库） 采用（维护者通道）
GitHub 网页预填链接 不需要 低（有 GitHub 账号即可） 高（不接触 token） 采用（公众通道）
Issue → Action 自动 PR 不需要 低 高 路线图
第三方托管 CMS（Decap/Pages CMS） 不需要 低 依赖第三方 备选

6.2 双通道设计

通道 A：GitHub 网页新建（免 Token）

CMS 组装 markdown
      │
      ▼
https://github.com/<owner>/<repo>/new/<branch>?filename=<path>&value=<urlencode(markdown)>
      │
      ▼
GitHub 网页编辑器已预填 → 用户点「Create a new branch」→「Propose changes」→ PR
  • 没有仓库写权限的访客会被 GitHub 引导 fork → 分支 → PR，属于标准 OSS 协作路径
  • 限制：/new 支持预填，/edit 不支持 → 编辑已存在文件时提供「复制 Markdown + 打开编辑页」两步流程

通道 B：PAT 直连 API（维护者）

一次点击完成 5 个请求：

GET  /repos/{o}/{r}/git/ref/heads/main          → base sha
POST /repos/{o}/{r}/git/refs                    → refs/heads/cms/<slug>-<stamp>
GET  /repos/{o}/{r}/contents/<path>?ref=<branch>→ 是否存在（取 sha）
PUT  /repos/{o}/{r}/contents/<path>             → utf-8 → base64 提交
POST /repos/{o}/{r}/pulls                       → PR（base=main, head=cms/...）

设计要点：

  • 分支名强制 ASCII（cms/x-mweq660），避免中文 ref 在 CI/工具链中的兼容问题
  • 中文正文用 TextEncoder + 分块 String.fromCharCode 转 base64（btoa 不能直接处理 Unicode）
  • 错误信息落到 UI：401/403/404/422 分别提示权限、仓库名、路径、校验
  • 整个流程没有任何服务器参与，token 只在本机内存/存储中

6.3 Token 安全模型

项 决策
权限 Fine-grained，仅本仓库：Contents: RW + Pull requests: RW + Metadata: R
存储 默认 sessionStorage（关标签页即失效）；勾选「记住设备」才写 localStorage
展示 输入框 type=password，任何日志/错误信息不回显 token
页面 加 CSP，script-src 'self'、connect-src 'self' https://api.github.com
第三方脚本 禁止（统计、字体 CDN 都不加），消除 token 侧信道
撤销 UI 一键清除 + README 说明 GitHub 侧撤销

残余风险：若站点自身存在 XSS，token 可被读取。当前站点无用户输入回显、无第三方脚本、CSP 收紧，攻击面极小；这也是"坚持零第三方依赖"的原因之一。

7. CI/CD 与质量门禁

PR 打开 ──► ci.yml
             ├─ pnpm install
             ├─ node scripts/validate-content.mjs   ← frontmatter/分类/id 校验
             ├─ pnpm run build                      ← 构建必须通过
             └─ upload-artifact(dist-preview, 7d)

合并 main ──► deploy.yml
              ├─ 同上校验 + 构建
              ├─ configure-pages
              ├─ upload-pages-artifact(dist)
              └─ deploy-pages → https://<owner>.github.io/<repo>/
  • 门禁的唯一真理是仓库状态：main 永远等于线上
  • 失败即红叉，审阅者可以只凭 PR 状态决定合不合
  • 后续可加：pr-preview-action（把 PR 构建发到 gh-pages/previews/pr-N/）、链接检查、拼写检查

8. 视觉系统：瑞士国际主义 + 工业风

8.1 设计原则

  1. 网格先于装饰：12 栏网格用极淡竖线显式画出，所有内容贴网格
  2. 字体即层级：只用一套无衬线（Helvetica/Arial），通过字重、字号、字距建立层级
  3. 三色系统：纸白 #F2F1EC / 墨黑 #121212 / 信号红 #E2231A，红只用于编号与强调
  4. 零圆角、零渐变、零阴影：用 1px 发丝线与 2px 粗线分隔
  5. 编号系统：导航 01/02/03、列表项两位置编号、文章 h2 自动 01/02/03（CSS counter）
  6. 左对齐 + 大留白：不做居中排版，标题可以压到很大

8.2 Token 表

Token 浅色 深色 用途
--paper #F2F1EC #101010 背景
--ink #121212 #F0EFE9 正文
--accent #E2231A #FF3B30 编号/强调
--rule #121212 #F0EFE9 分隔线
--grid 5.5% 透明 6% 透明 栏线

8.3 组件规则

  • 页眉：品牌左 / 编号导航中 / 搜索与主题开关右，底部 2px 墨线；窄屏导航折为第二行
  • Hero：巨型大写标题 + 右侧等宽统计（分类计数/总数），底部 1px 线
  • 列表行：编号 | 标题+摘要+标签 | 日期，hover 整行反白
  • 文章：面包屑 INDEX / 01 教程 / ID，标题 52px，h2 带等宽序号与顶部细线
  • 按钮/输入：矩形、1px 边框、等宽大写标签

9. 动效系统

原则：方向一致、无弹跳、只做一次。

场景 实现 参数
首页标题 每行遮罩（overflow:hidden + 内层 translateY(112%→0)） 0.9s cubic-bezier(.16,1,.3,1)，两行错开 100ms
路由切换 旧页淡出，新页下移 18px + clip-path 上滑揭开 出 0.18s / 入 0.42s，mode="out-in"
滚动揭示 IntersectionObserver + .reveal（透明度/位移/clip-path） 0.65s，列表 stagger 90ms
搜索浮层 从顶部 clip-path: inset(0 0 100% 0) 拉开 0.3s
导航下划线 scaleX(0→1)，原点在左 0.26s
文章 h2 细线 伪元素 scaleX 展开 0.7s
  • 正文由 v-html 生成，挂不上指令 → 提供 revealChildren() 对子节点批量观察
  • 全部动效在 prefers-reduced-motion: reduce 下被压缩为 0.001ms
  • 用 will-change 限于揭示元素，避免常驻合成层

10. 性能与体积

产物 体积 gzip
index.js（主包） ~155 KB ~60 KB
index.css ~19 KB ~5 KB
CmsView.js（懒加载） ~13 KB ~5 KB
  • CMS 走动态 import()，普通读者不会下载编辑器代码
  • 无字体文件、无图片依赖、无第三方脚本
  • 无运行时数据请求，首屏一次请求即完成
  • 图片走外链图床，不占产物体积

11. 安全与可访问性

11.1 安全

  • CSP：default-src 'self'; script-src 'self'; connect-src 'self' https://api.github.com; form-action 'none'
  • 无第三方脚本：消除供应链面
  • Token 最小权限：单仓库、仅内容与 PR 权限
  • 内容可信边界：Markdown 由审阅者过目；v-html 渲染的是仓库内文件，不接受用户输入注入

11.2 可访问性

  • 语义标签（header/nav/main/article/footer）、aria-label 覆盖搜索与主题按钮
  • 对比度：墨黑/纸白 ≈ 17:1；红色仅用于强调，不承担正文信息
  • 键盘可达：都是原生 a/button/input
  • 动效可关闭（系统级）

12. 风险与取舍

风险 影响 缓解
编辑者嫌 GitHub 流程麻烦 贡献量下降 A 通道尽量少点击；后续接 Issue 模板
PAT 泄露 仓库被写 细粒度 + 单仓库 + 一键撤销 + CSP 收紧
内容无预览 排版问题合并后才看到 Phase 2 加 PR 预览
仓库变大 clone 慢 图片外链、不存二进制
依赖 GitHub 平台绑定 内容为纯文件，可随时迁 GitLab/Pages CMS
手机端构建受限（FUSE） 本地构建需 build.sh CI 是权威构建环境，本地只是预览

14.3 部署检查清单

  1. src/config.js 填正确的 owner/name/branch
  2. Settings → Pages → Source: GitHub Actions
  3. Settings → Actions → Workflow permissions: Read and write
  4. 首篇 PR 合并后确认 Pages URL 生效
  5. 给维护者发放 fine-grained PAT（已按第 6.3 节限定范围）
